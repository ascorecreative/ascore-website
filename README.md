# Ascore Creative website

React 19 and Vite website with an original Blender metallic aperture hero and server-backed client and agency workspaces. The exact Ascore symbol, existing portfolio links and five actual service disciplines are retained. The original desktop and mobile videos are retained byte-for-byte and are loaded only as the fullscreen video handoff approaches.

## Local development

Use Node.js 24 (Node 22.13+ supports the SQLite API). Install dependencies with `npm ci`, then run `npm run dev:all`. This starts the loopback API on port 8787 and Vite on http://127.0.0.1:5173. Alternatively, run `npm run api` and `npm run dev -- --host 127.0.0.1 --port 5173 --strictPort` in separate terminals. Vite proxies `/api` to the local server. Keep `ASCORE_ORIGIN` exactly equal to the browser's origin.

`npm run build` creates the frontend bundle and prerendered physical page directories. `npm run lint` checks frontend source; `npm run test:portal` exercises the API against isolated in-memory databases and Zoho adapters against synthetic responses. `npm run preview -- --host 127.0.0.1 --port 5173 --strictPort` previews the bundle while the API runs separately.

## Blender hero

The active Blender source is `assets/blender/ascore-unified-sculpted.blend`, produced on the cloud workstation. `public/hero/ascore-unified-sculpted.glb` keeps the original seven metallic blades around a physically faceted interpretation of the exact symbol outline: 191,112 bytes / 3,388 triangles, eight clips and no textures, with a transparent WebP poster. The center uses rich teal/blue/indigo vertex colors on PBR metal, with no emissive front or logo decal. The original `ascore-idea-engine.blend` and GLB remain as source history; the later service-icon variant is not used.

Scroll opens and reassembles the aperture through the GLB's coordinated animation clips. A single animation mixer seeks the clips from section progress. The canvas uses demand rendering, bounded DPR, a locally generated environment, delayed enhancement and visibility gating. The poster remains available during loading and after WebGL failure. OS reduced motion avoids mounting WebGL; `?motion=reduce` and `?webgl=off` expose the same fallback paths for local QA. The sculpture stays centered and pinned within its hero scroll sequence, with reversible scroll scrubbing. Headline and supporting copy clear the object as the sequence opens; the fixed header contact action remains available. Compact phone and landscape layouts keep text separate from the sculpture. No remote HDRI is requested.

## Portal

`#login`, `#signup` and `#portal` use the same server-backed authentication. Clients register with a username, email and private password. They see only their own assigned projects, milestones, quotations and invoices. Agency users manage registered clients, leads, project stages and progress, quotations, invoices, internal bills and manually recorded settlements. Financial amounts are stored and calculated in minor currency units. Nothing charges customers, sends invoices, creates payment links or performs a banking transaction.

The local SQLite database is created empty under ignored `server/data/`. Passwords use salted scrypt. Sessions use hashed opaque tokens with HttpOnly/SameSite cookies; mutations require the configured origin and session CSRF token. Production requires HTTPS, Secure cookies and explicit registration enablement. Authentication attempts and hash concurrency are bounded. Do not use old browser-storage demo records as real client records: they are not imported into this backend. Pre-existing local demo UI files remain unused and are excluded from this change to preserve prior work; legacy database access now fails explicitly.

### Private admin activation

The exact usernames `aswinfrn` and `sachindinesh` are reserved. Neither account is seeded or activated. No default password or usable setup token is included. An operator must separately approve each activation, configure `ASCORE_ALLOW_ADMIN_SETUP=1`, and supply a private, expiring grant in `ASCORE_ADMIN_SETUP_GRANTS`. Each entry contains the SHA-256 hash of a securely generated private token and an ISO expiry, keyed by the exact username. The operator provides the actual token privately to its intended administrator, who chooses and submits their own password (15–128 characters) in Agency account setup. Tokens are single-use and their consumption persists in SQLite. Disable setup and clear configured grants after activation. Admin accounts do not require an email address.

The production setup is incomplete until hosting, TLS, durable database backups, monitoring, credential operations and identity-verified password recovery are configured and reviewed. Password recovery, email verification and MFA are not implemented in this draft. No production accounts were created during development.

## Zoho CRM and Books

The website requires its **own separately approved server credentials**. Existing assistant connector access is not reused. Copy `.env.example` to ignored `.env.server` only in an approved environment. Never prefix a secret with `VITE_`. API tokens must be provisioned and rotated through an approved OAuth flow; automated OAuth refresh is not configured in this draft.

CRM uses v8 Leads and Contacts. Books uses Customers/Vendors, Estimates (quotations), Invoices and Bills. Projects and milestones stay in the portal because no corresponding supported CRM/Books project module is assumed. The Connections page verifies the expected CRM organization and Books organization against the server credentials, can verify/link exact existing record IDs, and previews outgoing record payloads before a manual sync. CRM stage values require a configured picklist map. Financial sync additionally requires verified Books customer/vendor links, service item ID, currency and tax mappings. Currency or tax mismatches block a write instead of guessing.

`ASCORE_ENABLE_ZOHO_WRITES=0` is the default. Live sync requires separately approved credentials, organization verification, explicit enablement and confirmation of the exact reviewed payload. No live Zoho calls were made during implementation. CRM workflows are not requested (`trigger: []`); financial records are not sent to recipients or marked paid. Local offline payment records never trigger Zoho payment creation. Unknown write outcomes persist as uncertain and do not retry automatically; inspect Zoho and reconcile the exact record before another attempt.

The manual Books balance refresh reads up to 25 linked records and displays timestamped remote balances separately from the local manual ledger. It does not overwrite local settlements. This draft does not implement background or conflict-resolving two-way synchronization. Website OAuth credentials and Books account verification remain setup blockers.

Official API references: [CRM insert records](https://www.zoho.com/crm/developer/docs/api/v8/insert-records.html), [Books API](https://www.zoho.com/books/api/v3/introduction/), [Books estimates](https://www.zoho.com/books/api/v3/estimates/).

## Deployment

No publishing or deployment is performed by this change. A production host must serve `dist/` and route `/api` to the Node server behind an approved HTTPS reverse proxy. Keep the Node listener private, set the exact HTTPS `ASCORE_ORIGIN`, provide persistent SQLite storage and backups, and never commit `.env.server`, access tokens, setup grants or database files.
